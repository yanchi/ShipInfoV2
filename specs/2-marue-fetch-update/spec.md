# Feature Specification: マルエーフェリー情報取得方式変更

**Feature Branch**: `2-marue-fetch-update`
**Created**: 2026-03-08
**Status**: Draft
**Input**: User description: "マルエーフェリーの情報取得処理変更：検索エンドポイントへのPOSTで本日の運航有無を確認し、鹿児島航路ページからステータス詳細を取得する"

## 背景

現在のマルエーフェリースクレイパーは `/status/` ページの h3/h4 要素を解析して運航状況を取得している。
この方式を2ステップ方式に変更する：

1. 検索エンドポイント（`/search/result.php`）への出港地（50）・入港地（83）・日付指定POSTで本日便の有無を確認
2. 鹿児島航路ページ（`/kagoshima/`）から詳細ステータスを取得

---

## Clarifications

### Session 2026-03-08

- Q: 上り便（那覇→鹿児島）の運航有無確認方法 → A: 検索POSTは下り便（startPort=50, endPort=83）のみ実行し、便の有無を上り・下り両方向に共通の判定として扱う。上り・下り各方向の詳細ステータスは鹿児島航路ページ（`/kagoshima/`）から取得する。
- Q: `valid_date` の取得元 → A: POSTパラメータ `startDate`（= `date.today()`）をそのまま `valid_date` として使用する。レスポンスHTMLのパースは不要。便なし時も同様に `date.today()` を使用する。
- Q: 鹿児島航路ページから取得する日付範囲 → A: 当日分（today）のみ取得・保存する。
- Q: 鹿児島航路ページで当日のステータスが見つからない場合 → A: warning ログを記録し、そのレコードはスキップ（保存しない）する。

## User Scenarios & Testing

### User Story 1 - 本日の運航有無を検索APIで確認 (Priority: P1)

スクレイパーが検索エンドポイントに本日の日付・出港地・入港地を指定してリクエストを送り、便の有無から「運航あり/なし」を判定する。

**Why this priority**: 運航の有無はステータス取得より前に確定させる必要があり、最も基礎的な判定ロジック。

**Independent Test**: `make scraper-run` 実行後に `operation_statuses` テーブルへマルエーフェリーのレコードが保存され、便なしの日に `cancelled` 相当のステータスが記録されること。

**Acceptance Scenarios**:

1. **Given** 本日の便が存在する場合、**When** 検索エンドポイントにPOSTリクエストを送信、**Then** レスポンスに結果が含まれ「運航あり」と判定される
2. **Given** 本日の便が存在しない場合、**When** 検索エンドポイントにPOSTリクエストを送信、**Then** レスポンスに結果がなく「運航なし」として `operation_statuses` に記録される
3. **Given** 検索エンドポイントが 5xx を返す場合、**When** スクレイパーを実行、**Then** リトライ後に `scraper_logs` へエラーが記録され、他社の処理は継続される

---

### User Story 2 - 鹿児島航路ページから詳細ステータスを取得 (Priority: P2)

「運航あり」と判定された場合、鹿児島航路ページを取得し、上り・下り各方向の詳細ステータス（通常運航・条件付き運航・欠航等）を解析して上り便・下り便それぞれ保存する。

**Why this priority**: P1 で運航有無が確定してからステータス詳細を取得するため、P1 依存。

**Independent Test**: 条件付き運航日に `make scraper-run` を実行すると `operation_statuses` に上り便・下り便それぞれの `delayed` ステータスが保存されること。

**Acceptance Scenarios**:

1. **Given** 鹿児島航路ページが通常運航を示している場合、**When** スクレイパーが解析、**Then** `operating` ステータスで保存される
2. **Given** 鹿児島航路ページが条件付き運航を示している場合、**When** スクレイパーが解析、**Then** `delayed` ステータスと詳細テキストで保存される
3. **Given** 鹿児島航路ページが欠航を示している場合、**When** スクレイパーが解析、**Then** `cancelled` ステータスで保存される
4. **Given** 同一 `route_id + valid_date` のデータがすでに存在する場合、**When** 再度スクレイプ、**Then** 重複レコードは作成されない

---

### Edge Cases

- 検索エンドポイントのレスポンス構造が変わった場合: warning ログを記録し、安全側（運航ありとして鹿児島航路ページに進む）に倒す
- 検索レスポンスに日付が含まれない場合: `valid_date = today` をフォールバックとして使用し、warning ログを記録する
- 鹿児島航路ページのHTML構造が変わった場合: warning ログを記録し、`scraper_logs` を `failed` で記録
- 鹿児島航路ページに当日分のステータスが存在しない場合: warning ログを記録し、当該方向のレコードはスキップ（保存しない）
- **複数船のステータスが混在する場合**: 最も深刻なステータスを採用する（優先度: `cancelled` > `suspended` > `delayed` > `operating`）。混在が発生した場合は warning ログを記録する。根拠: 乗客への安全通知として、最も制限的な情報を提示することが適切なため
- 検索エンドポイントで「便なし」なのに鹿児島航路ページが異常ステータスを示す場合: 検索結果（「運航なし」）を優先する
- ネットワークタイムアウト/5xx: 既存のリトライロジック（最大3回、backoff_factor=1.0）を踏襲

## Requirements

### Functional Requirements

- **FR-001**: System MUST 検索エンドポイントへのPOSTリクエストで下り便（鹿児島→那覇）の有無を確認し、その結果（便の有無と運航日付）を上り・下り両方向に共通の判定として扱うこと
- **FR-002**: System MUST 検索結果が空の場合、対象航路を「運航なし」として `operation_statuses` に記録すること
- **FR-003**: System MUST 検索結果がある場合、鹿児島航路ページから当日分の詳細ステータス（通常・条件付き・欠航・運休）を上り・下り各方向について取得すること。当日分が見つからない場合は warning ログを記録しスキップすること
- **FR-004**: System MUST 取得した詳細ステータスを既存の `OperationStatusEnum` にマッピングして保存すること
- **FR-005**: System MUST 既存の重複防止ロジック（`raw_html_hash`）を維持すること
- **FR-006**: System MUST 既存のリトライロジック・エラーログ記録を維持すること
- **FR-007**: System MUST 1社のスクレイピング失敗が他社の処理をブロックしないこと

### Key Entities

- **検索リクエスト**: 下り便用の出港地コード（50）・入港地コード（83）・対象日付を持つ。結果は上り・下り両方向の運航有無判定に共用する
- **検索レスポンス**: 便の有無（二値）と `valid_date`（運航日付）を含む。便なしの場合は `valid_date = today` をフォールバックとして使用
- **運航有無判定結果**: 便あり/なしの二値
- **OperationStatus**: 運航状況レコード（`valid_date` + `route_id` がキー）。取得方式変更後も既存スキーマを維持

---

## Success Criteria

### Measurable Outcomes

- **SC-001**: `make scraper-run` 実行後、5分以内にマルエーフェリーのレコードが `operation_statuses` に保存される
- **SC-002**: 便なしの日は「運航なし」ステータスが正しく記録される（誤検知なし）
- **SC-003**: 同じデータを2回スクレイピングしても `operation_statuses` の件数が増えない
- **SC-004**: マルエーフェリーのスクレイピングが失敗してもマリックスラインは正常完了する
- **SC-005**: `scraper_logs` で実行結果・エラー内容が確認できる
