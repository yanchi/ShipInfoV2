# Feature Specification: マルエーフェリーの抜港を取りこぼさない

**Feature Branch**: `9-marue-port-skip`
**Created**: 2026-10-06
**Status**: Draft
**Input**: User description: "マルエー公式サイトは抜港なのに本サイトは決行になってる"

## 概要

2026-10-05〜06 の荒天で、マルエーフェリー「フェリー波之上」の 10/5 鹿児島新港 18:00 発・下り便が「スケジュール変更・条件付運航」になり、和泊港・与論港が抜港（寄港しない）になった。公式サイトではこの2港が抜港なのに、本サイトでは同じ港の行が「通常運航」（または運航する扱い）で出ている時間帯があった。

抜港の港を「運航する」と出すのは、本サイトで一番やってはいけない誤り。利用者がその港へ行っても船は来ないので、見逃したら移動・宿泊の予定が崩れる。本機能では、公式サイトが「その港には寄らない」と書いているときに、本サイトがその港を運航する扱いで出さないようにする。

### 2026-10-06 09:28 時点の公式サイト（`samples/` に保存）

鹿児島航路ページの船ブロック（フェリー波之上）:

- ステータスのタグは **2つ**：「スケジュール変更」「条件付運航」
- 抜粋：「10/5(月)鹿児島新港18:00発／下り便…スケジュール変更・条件付運航」

船別詳細ページの本文（抜粋）:

```
10月5日(月)鹿児島新港　　　　　/18:00(出港)
10月6日(火)名瀬港　5:00(入港)/5:50(出港)
10月6日(火)亀徳港　9:10(入港)/9:40(出港)
10月6日(火)和泊港 抜港
10月6日(火)与論港 抜港
10月6日(火)本部港　14:20(入港)/16:30(出港)
10月6日(火)那覇港　18:20(入港)
※条件付寄港地 : 亀徳港(徳之島)
※和泊港(沖永良部島)・与論港(与論島)には寄港いたしません。
```

同じ時点の本サイトは和泊・与論の行を「欠航」で出していた（この時点の本文には「和泊港 抜港」の行があるため）。

### 考えられる原因（調査結果。詳細は plan で確定する）

1. **「寄港いたしません」を抜港として読めていない**。今は「抜港」という語だけを抜港として扱っている。公式の告知が「和泊港・与論港には寄港いたしません」だけの書き方だと、2港は「言及の無い港」になる
2. **条件付の船で、言及の無い港を「通常運航」にしている**（specs/4-departure-port-status FR-006 のただし書き）。1 と重なると、抜港の港が「通常運航」になる。公式の告知が更新途中（抜港の行がまだ無い・本文が取れない）のときも同じことが起きる
3. **ステータスのタグを最初の1つしか見ていない**。「スケジュール変更」「条件付運航」の2つが付いていると、最初の「スケジュール変更」だけを見て、条件付の船と扱わない。タグの並びや組み合わせによって港の判定が変わってしまう
4. **便の説明に出てくる港を、条件付の対象と取り違える**。抜粋「鹿児島新港18:00発／下り便…条件付運航」の鹿児島新港が「条件付」の対象になっている（港名と「発」のあいだに時刻があるため、便の説明と見分けられていない）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 抜港の港は「欠航」で出る (Priority: P1)

和泊港から乗る予定の利用者が本サイトの港別ページで 10/6 の「和泊発→那覇」を見る。公式サイトが和泊港を抜港（寄港しない）としているなら、本サイトでも「欠航」と出て、公式の説明文が添えられている。公式が「抜港」と書いても「寄港いたしません」「寄港しません」と書いても同じように出る。

**Why this priority**: 抜港の港を「運航する」と出すと、利用者は来ない船を待つことになる。本サイトの信頼に直結する一番重い誤り。

**Independent Test**: 公式の本文が「抜港」の場合、「寄港いたしません」だけの場合のそれぞれで、その港の行が「欠航」になることを、保存した公式ページ（または同じ文面）で確かめられる。

**Acceptance Scenarios**:

1. **Given** 船別詳細ページに「10月6日(火)和泊港 抜港」がある、**When** 和泊発の行を見る、**Then**「欠航」と出て、抜港を書いた公式の文が添えられている
2. **Given** 本文に「抜港」の語が無く「※和泊港(沖永良部島)・与論港(与論島)には寄港いたしません。」だけがある、**When** 和泊発・与論発の行を見る、**Then** 両方「欠航」と出る
3. **Given**「与論港には寄港しません」「与論港への寄港を取りやめ」「与論港は通過」のような言い方、**When** 与論発の行を見る、**Then**「欠航」と出る
4. **Given**「天候により与論港に寄港しない場合があります」のような仮定の文だけがある、**When** 与論発の行を見る、**Then**「欠航」にはしない（船全体のステータスのまま）

---

### User Story 2 - 公式が異常を出しているのに「通常運航」と出さない (Priority: P1)

公式サイトでその船に「条件付運航」「スケジュール変更」などが出ているとき、本サイトの港の行が根拠なく「通常運航」にならない。公式の告知が書きかけ・読み取れない書き方・詳細ページが取れないなどで、港ごとの扱いを読み切れないときは、安全側（条件付・遅延）に倒す。

**Why this priority**: 読み取りの取りこぼしは今後も起きうる。取りこぼしたときに「通常運航」に落ちる作りだと、どんな書き方の変化でも同じ事故になる。取りこぼしても「条件付・遅延」で出れば、利用者は公式を確認しに行ける。

**Independent Test**: 条件付の船で、本文に港の言及があるが一部の港しか読めない／寄港しない旨の文があるのに港を特定できない、などの文面で、言及の無い港が「通常運航」にならないことを確かめられる。

**Acceptance Scenarios**:

1. **Given** 条件付の船で、本文が「条件付寄港地：亀徳港」と、港を特定できない「寄港いたしません」の文を含む、**When** 亀徳以外の港の行を見る、**Then**「通常運航」ではなく「条件付・遅延」と出る
2. **Given** 条件付の船で、本文に各港の入出港時刻の一覧があり、和泊港・与論港が一覧で「抜港」、名瀬港・本部港に時刻がある、**When** 名瀬発・本部発の行を見る、**Then** 和泊・与論は「欠航」、亀徳は「条件付・遅延」、名瀬・本部は今と同じ判定（言及の無い港の扱い）になる
3. **Given** 条件付の船で、船別詳細ページが取れなかった、**When** その船の便の各港の行を見る、**Then** どの港も「通常運航」にはならない

---

### User Story 3 - タグが複数あっても判定がぶれない (Priority: P2)

公式の船ブロックにステータスのタグが複数付いている（「スケジュール変更」＋「条件付運航」など）とき、タグの並び順に関係なく、すべてのタグを踏まえて船のステータスと条件付かどうかを決める。

**Why this priority**: 今回の便で実際に起きている。タグの並びが変わるだけで港の判定が変わるのは不安定。ただし US1・US2 が入れば利用者に見える誤りの大部分は防げるので P2。

**Independent Test**: 2つのタグを入れ替えた船ブロックで、船のステータスと港ごとの判定が同じになることを確かめられる。

**Acceptance Scenarios**:

1. **Given** タグが「スケジュール変更」「条件付運航」の順、**When** 判定する、**Then** 船は条件付・遅延で、条件付の船として港別情報を当てる
2. **Given** 同じタグが逆の順、**When** 判定する、**Then** 1 と同じ結果
3. **Given** タグが「欠航」と他のタグの組み合わせ、**When** 判定する、**Then** 一番重いもの（欠航）になる

---

### User Story 4 - 便の説明に出てくる港を条件付にしない (Priority: P3)

抜粋「10/5(月)鹿児島新港18:00発／下り便…スケジュール変更・条件付運航」のように便を説明する港（鹿児島新港）を、条件付の対象の港と取り違えない。

**Why this priority**: 誤って「条件付・遅延」になる向き（安全側）の誤りなので害は小さい。ただし「出港済み」の始発港に紛らわしい表示が出る。

**Independent Test**: 上の抜粋だけを読ませて、鹿児島新港が対象の港にならないことを確かめられる。

**Acceptance Scenarios**:

1. **Given** 抜粋「10/5(月)鹿児島新港18:00発／下り便…スケジュール変更・条件付運航」、**When** 港別情報を読む、**Then** 鹿児島新港は対象の港にならない
2. **Given**「鹿児島新港 18:00発の便は与論港を抜港」、**When** 港別情報を読む、**Then** 与論港だけが抜港になる

---

### Edge Cases

- 1つの告知に同じ港が「抜港」と「条件付寄港」の両方で出る → 抜港を優先する（今と同じ）
- 告知の港一覧で「抜港」の行と、末尾の「寄港いたしません」の文が同じ港を指す → 1件の抜港として扱う
- 「寄港いたしません」の文に港名が無い・航路外の港しか無い → 港は特定しない。条件付の船なら言及の無い港を「通常運航」にしない（US2）
- 別の便（上り便など）について「寄港しません」と書いてある → その告知が対象とする便の港だけに当てる（FR-007 の考え方を引き継ぐ。告知の便と今の便の対応が付かないときは今と同じ扱い）
- 出港済みの行は今と同じく確定させる。ただし抜港の港は実際には「出港」しないので、予定出港時刻を過ぎたあとに抜港が分かった場合も「欠航」に直す（FR-011）
- マリックスラインの便は今回の対象外（便別詳細ページに港別ステータスが構造化されていて、本サイトでも「寄港しません」で欠航になっている）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: マルエーフェリーの運航状況テキストで、「抜港」に加えて「寄港いたしません」「寄港しません」「寄港を取りやめ」「寄港を見合わせ」「通過」など、その港に寄らないことをはっきり書いた表現を抜港として扱い、その港の行を「欠航」にしなければならない
- **FR-002**: 仮定・案内の文（「〜の場合」「〜することがあります」「〜の可能性」など）の寄らない表現は抜港として扱ってはならない（今の除外ルールを引き継ぐ）
- **FR-003**: 船が条件付・遅延・スケジュール変更のとき、港の行を「通常運航」にしてよいのは、告知がその便の港別の扱いを読み切れたときに限らなければならない。次のどれかに当たるときは、言及の無い港を船全体のステータス（条件付・遅延）のままにする:
  - 寄らない旨・条件付の旨の文があるのに、対象の港を特定できなかった
  - 船別詳細ページが取れなかった・本文の区切りが見つからなかった
- **FR-004**: 船のステータスは、船ブロックに付いているすべてのタグから決めなければならない。複数のタグがあるときは一番重いもの（欠航 > 運休 > 条件付・遅延 > 通常運航）にし、どれか1つでも「条件付」なら条件付の船として扱う。タグの並び順で結果が変わってはならない
- **FR-005**: 港名のあとに日付・時刻をはさんで「発」「着」が続く場合（「鹿児島新港18:00発」）も、便・航路の説明として港別情報の対象から外さなければならない
- **FR-006**: 抜港と判定した港の行には、その根拠になった公式の文を詳細テキストとして添えなければならない（今の表示と同じ）
- **FR-007**: 抜港・条件付の判定が変わって港の行が「欠航」「条件付・遅延」になったら、既存の通知（運航に変更がある便の通知メール）の対象にも同じ判定が使われなければならない（通知は港の行のステータスを見ているので、判定を直せば通知も直る想定。別の仕組みは作らない）
- **FR-008**: 今回の公式ページ（2026-10-06 時点の鹿児島航路ページと「フェリー波之上」の船別詳細ページ）を再現データとして残し、そのページから和泊・与論が「欠航」、亀徳が「条件付・遅延」、鹿児島新港が対象外になることを自動テストで確かめられなければならない。「抜港」の行を取り除いて「寄港いたしません」の文だけにした版でも同じ結果になること
- **FR-009**: 港の行のステータスの種類・表示ラベル・色は変えない（specs/4-departure-port-status FR-011 を引き継ぐ）
- **FR-010**: 港別情報が取れても読めなかったとき（条件付の船で港を特定できない寄らない旨の文があったときなど）は、元の文面が追えるように記録を残さなければならない（今の「条件付なのに港別情報が読めなかった」記録と同じ考え方）
- **FR-011**: 抜港の港には船が来ないので、その港の予定出港時刻を過ぎたあとに抜港が分かった場合でも、その行を「欠航」に直さなければならない（出港済みの行を確定させる今のルールの例外。抜港以外の判定は今のまま確定させる）

### Key Entities

- **船ブロックのステータス**: 鹿児島航路ページの船ごとのタグ（複数あり得る）・抜粋・詳細ページへのリンク。タグの組み合わせから船全体のステータスと「条件付かどうか」を決める
- **港別情報（告知）**: 船別詳細ページの本文から読み取る港ごとの扱い（抜港・港変更・条件付寄港）と根拠の文。今回、寄らない旨の表現と「読み切れたかどうか」を持たせる
- **港の行（出発港別の便）**: 出発港 × 方向 × 出港日の行。今の便の行に船全体のステータスと港別情報を重ねて決める（既存）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 2026-10-06 の公式ページ（保存版）と、その「寄港いたしません」だけ版のどちらでも、和泊発・与論発の 10/6 の行が 100% 「欠航」になる
- **SC-002**: 公式の船ステータスが通常運航以外の船について、本サイトの港の行が「通常運航」になるのは、公式の告知でその港が問題なく寄港すると読み取れた場合だけになる（テストで用意した取りこぼしの文面すべてで「通常運航」が0件）
- **SC-003**: 船ブロックのタグの並びを入れ替えても、全港の判定結果が変わらない
- **SC-004**: 今ある港別情報のテスト（通常運航の詳細ページで港別情報が0件、など）がすべて通り、通常運航の日に誤って「欠航」「条件付・遅延」になる港が増えない
- **SC-005**: 公式が抜港を告知してから、本サイトの該当港の行が「欠航」になるまでの時間が、次のスクレイピング1回分（今の実行間隔）以内

## Assumptions

- ユーザーの言う「決行」は、本サイトの「通常運航」（または運航する扱いの表示）を指していると解釈した。本サイトに「決行」という表示は無い
- 不具合を見た正確な時刻と画面は分からない。09:28 時点では本サイトは和泊・与論を「欠航」で出していたので、それより前の、公式の告知が「寄港いたしません」の書き方だけだった／書きかけだった時間帯に起きたと推定した（原因 1・2）。原因 3 は今の公式ページで実際に起きている
- 寄らない旨の表現のリストは、今回の文面と一般的なフェリー会社の告知の言い回しから決めた。新しい言い回しが見つかったら追加する
- 「言及の無い港は通常運航」のルール（specs/4 FR-006）は、告知を読み切れたときに限って残す。これをやめてすべて「条件付・遅延」にすると、条件付の理由と無関係な港まで警告が出て、通知メールが増えすぎるため
- マリックスラインのスクレイパー・画面の表示・通知メールの仕組み自体は変えない
- 過去に誤って「通常運航」で記録された行のさかのぼり修正はしない（出港済みの行は確定扱いのまま）

## Out of Scope

- マリックスラインの港別ステータスの読み方の変更
- 「スケジュール変更」で変わった入出港時刻を港の行の時刻に反映すること（便検索の時刻を使う今の扱いのまま）
- 告知の文面を AI などで自由に読み取る仕組み
- ステータスの種類（「抜港」専用の表示など）を増やすこと
