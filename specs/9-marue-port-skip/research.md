# Research: 抜港を「抜港」と表示する

**Spec**: [spec.md](spec.md) | **Date**: 2026-10-06

調べた元：`samples/` の保存版（2026-10-06 09:28）、`scraper/scraper/utils/port_notice.py`、`scraper/scraper/scrapers/marue_ferry.py`・`marix_line.py`、`app/src/Enum/OperationStatusEnum.php`、`app/src/View/PortBoardEntry.php`、テンプレートと既存の fixture。

---

## R1. 「抜港」の値をどこに持つか

**Decision**: 既存の `OperationStatusEnum`（PHP・Python とも）に `skipped`（文言「抜港」）を足す。DB のマイグレーションはしない。

**Rationale**:
- `departure_statuses.status` は `VARCHAR(32)`（Python も文字列で持つ）なので、値を足すだけで入る
- 港別の行を扱う Builder・Collector・テンプレート・通知メールは全部 `OperationStatusEnum` を見ている。別の enum にすると、その全部に分岐と変換が要る
- `operation_statuses.status` は MySQL の `ENUM(...)` だが、`skipped` はスクレイパーが航路単位で書かない（FR-011）。航路単位を作るのは `parse()` の `_route_status()`（マルエー）と一覧のクラス判定（マリックス）だけで、どちらも `skipped` を返す経路が無い。テストで確かめる

**Alternatives considered**:
- `DepartureStatusEnum` を新しく作る → 2つの enum の変換と、`label()`・`isIrregular()` の二重管理が負債になる。今の規模では割に合わない
- `status_detail` に「抜港」を書いて `cancelled` のまま → 欠航と区別できない（今回の不具合そのもの）

## R2. マルエーで「寄らない」を読み取る表現（FR-006）

**Decision**: `port_notice.py` の `skip` のキーワードを、「抜港」の1語から次の正規表現に広げる。

```
抜港
|寄港(?:いたし|致し|し)ません
|寄港(?:を|は)?(?:取りやめ|取り止め|とりやめ|見合わせ|中止)
```

仮定・案内の文を除く今のルール（`場合`・`ことがあります`・`可能性`・`問い合わせ`）はそのまま。「寄港しない場合があります」は除外で落ちる。

**Rationale**: spec FR-006 の4つ（寄港いたしません・寄港しません・寄港を取りやめ・寄港を見合わせ）と、その表記ゆれ（致し・取り止め・とりやめ・「寄港は」）、「寄港中止」まで。「寄港しない」（言い切りの普通形）は告知で使われにくく、「寄港しないことがあります」のような案内文で使われやすいので入れない。

**Alternatives considered**: 「寄港」を含むだけで拾う → 「条件付寄港地」「寄港後」で誤判定する。

## R3. 港名の後ろの括弧書き（保存版で見つけた取りこぼし）

**Decision**: 港別情報を読み取る前に、文から括弧書き `(…)`・`（…）` を取り除く。根拠として残す文（`PortNotice.sentence`、詳細テキスト）は元の文のまま。

**Rationale**: 保存版の「※和泊港(沖永良部島)・与論港(与論島)には寄港いたしません。」を今のロジックに通すと、

- 「与論島」の中の「与論」も港として見つかる（別名 `与論`）
- キーワードの直前の港は括弧の中の「与論」で、そこから前の「与論港」とのあいだが「(」なので列挙が切れる

→ 与論だけになり、和泊を取りこぼす。括弧を取ると「和泊港・与論港には寄港いたしません」になり、今の列挙ルールで2港とも拾える。

ついでに次の文も安全側に変わる。
- 「10月6日(火)和泊港 抜港」→ 曜日の括弧が消えるだけで結果は同じ
- 「スケジュール変更および条件付き運航(港変更や抜港、入出港時間などの変更を含む)といたします」→ 今は括弧の中の読点で節が割れて「1つの節に複数の種類」で捨てている。括弧を取ると「条件付」の節だけになり、対象の港は無い（鹿児島新港発は便の説明として除外）ので、結果は同じ

**Alternatives considered**: 列挙のすき間に括弧書きを許す（`_LIST_GAP` を広げる）→ 括弧の中の島名が別名に当たる問題が残る。

## R4. マルエーの複数タグ（FR-007）

**Decision**: `div.tag-list span` を全部読む。

- `status`：読み取れたタグのうち一番重いもの（欠航 > 運休 > 条件付・遅延 > 通常運航。既存の `_SEVERITY`）。1つも読めなければ None
- `conditional`：どれか1つに「条件付」がある
- `schedule_changed`（新規）：どれか1つに「遅延」「スケジュール変更」がある
- 読めないタグは `unknown_status_text` の warning を出して無視する

**Rationale**: 並び順で結果が変わらない（SC-004）。保存版のタグは「スケジュール変更」「条件付運航」の2つで、今は先頭だけを見て `conditional=False` になっている。

## R5. 言及の無い港の扱い（条件付 × スケジュール変更）

**Decision**: 今の「条件付の船で港別情報があれば、言及の無い港は通常運航」は、`schedule_changed` でない船にだけ当てはめる。スケジュール変更・遅延のタグもある船は、言及の無い港も船のステータス（条件付・遅延）のまま。

| タグ | 言及された港 | 言及の無い港 |
|---|---|---|
| 条件付運航 だけ | 抜港 / 条件付・遅延 | 通常運航（今のまま） |
| スケジュール変更 / 遅延 だけ | 抜港 / 条件付・遅延 | 条件付・遅延（今のまま） |
| 条件付運航 ＋ スケジュール変更 | 抜港 / 条件付・遅延 | **条件付・遅延** |

保存版では、和泊・与論＝抜港、亀徳＝条件付・遅延、鹿児島・名瀬・本部＝条件付・遅延になる。

**Rationale**: スケジュール変更の便は、言及の無い港も入出港の時刻が変わっている（保存版でも名瀬・本部の時刻が通常と違う）。時刻の反映は spec の対象外なので、「通常運航」と出すと古い時刻のまま安心させてしまう。FR-007 の「条件付の船として扱う」は、`conditional` の判定（抜港・条件付寄港の読み取りと `port_notice_unmatched` の warning）に効かせる。

**Alternatives considered**: 条件付が1つでもあれば言及の無い港を通常運航 → 上の理由で、スケジュール変更の便を「通常運航」と出してしまう。

## R6. 抜港の港の便検索に時刻・便が無いとき（Edge Case）

**Decision**:
1. 便検索の行で、マルエーの船なのに日時が「－」などで読めないときは、検索全体を失敗にせず、日時 None の行として残す（warning `search_datetime_missing`）
2. `parse_departures()` で、日時 None の行は「その船の今の便が同じ航路にあり、その港が抜港」なら `skipped`（時刻なし）。そうでなければ書かない（今までどおり次の実行で取り直す扱いと同じ。warning）
3. 検索結果が0件の港でも、ある船の今の便がその航路にあり、告知でその港が抜港なら、`no_service` の代わりに `skipped` の行（船名つき・時刻なし）を作る。出港日は「今の便の下船日 −（終点の `day_offset` − その港の `day_offset`）」

**Rationale**: 2026-10-06 の本サイトは和泊発・与論発を「欠航」で出していた。欠航になるのは検索に船の行があったときだけなので、今回は検索に便が出ていた。ただ、ほかの日に便が消えたり時刻が「－」になったりすると「便なし」や行の欠落になり、FR の「時刻が取れないことで便なしにしない」を破る。3 の出港日の計算は `route_stops.day_offset`（下り：和泊・与論・那覇とも1、上り：与論・和泊0／鹿児島1）で決まる。

**Alternatives considered**: 検索結果に便が出ている前提にして何もしない → 実例が無いぶん想定外のときに「便なし」と出て、今回と同じ種類の誤解（便が無い）になる。

## R7. マリックスラインの「寄港しません」（FR-004）

**Decision**: 詳細ページの `div.single.no_status` を `cancelled` から `skipped` に変える。詳細テキストは今と同じく `div.exp`（「寄港しません」）を使う。港のクラスがはっきり `cancel` のときは `cancelled` のまま。

**Rationale**: fixture `downstream_route_change.html` で、`no_status` の港の `div.exp` は「寄港しません」。FR-008 の根拠の文はそのまま取れる。

## R8. 抜港のバッジ（Clarifications：中間色）

**Decision**:

| | 値 |
|---|---|
| 記号・文言 | `≫ 抜港` |
| バッジ | 背景 `#ffe0c2`、文字 `#8a3b00`（コントラスト比 6.2:1。条件付・遅延は 5.0:1、欠航は 8.3:1） |
| 異常の行 | 左の線 `#8a3b00`、背景 `#fff3e8` |

**Rationale**:
- 色相：欠航（赤 `#f8d7da`/`#721c24`）と条件付・遅延（黄 `#fff3cd`/`#856404`）のあいだのオレンジ
- 記号：「≫」は JIS X 0208 にあり、日本語フォントで必ず出る。「通り過ぎる」に読める。既存の ✓ ○ ▲ ✗ ■ — ？ のどれとも形が違う（SC-007 の「記号と文言だけで区別」）
- 出港済みにしない（FR-009）：`isAlert()` に入れれば、今の `isDeparted()` が異常の行を除外している

**Alternatives considered**: 「↷」→ 日本語フォントに無い環境がある。「⊘」→ 欠航の ✗ と意味が近く見える。

## R9. 通知メール（US2）

**Decision**: `isIrregular()` に `Skipped` を入れるだけ。テンプレート・送信ルールは変えない。

**Rationale**: 本文の港の行は `port.status.label()`、対象は `irregularCases()`（`DepartureStatusRepository::findIrregularBetween`）。どちらも enum から決まるので、値を足せば「抜港」で出る。前回「欠航」・今回「抜港」の扱いは既存のルール（回ごとに1通、その時点の状態を全部書く）のまま。
