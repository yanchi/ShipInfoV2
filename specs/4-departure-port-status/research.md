# Research: 出発港別の運航情報表示

**Feature**: 4-departure-port-status
**Date**: 2026-10-01

すべて 2026-10-01 に実サイト・実環境で確認した内容。サンプル HTML は実装時に `scraper/tests/fixtures/` へ保存してテストに使う。

## R1. マリックスライン 便別詳細ページの構造

**確認 URL**: `https://marixline.com/service/upstream20260930/`（運航状況一覧の各便 `a.status_single` の href）

```html
<div class="service">
  <div class="single firstport normal">            <!-- 港ごとに1ブロック。class で状態 -->
    <div class="port sub">
      <span class="island">沖縄</span>
      <span class="port_name">那覇港</span>
    </div>
    <div class="service_single_inner">
      <div class="status sub">…svg… 通常運航</div>
      <div class="exp sub">定刻通りの運航を予定しています</div>
      <div class="departure sub long"><span class="label">出<br>港</span> 09月30日 07:00</div>
      <!-- 途中港は「入港」「出港」の2つ、終点は「入港」のみ -->
    </div>
  </div>
  <div class="single conditional alert"> … 与論港 … 条件付運航 … </div>
  …（7港）
</div>
```

- 港ごとの状態は `div.single` の class で判定できる（一覧ページと同じ語彙：`normal` / `conditional`+`alert` / `alert`）。
- 出入港日時は `MM月DD日 HH:MM` で、**年が無い**。URL 末尾の `upstream20260930` / `downstream20260930`（始発日）から年を補う。12/31 発 → 1/1 着のような年またぎは「始発日より前の月日なら翌年」で処理する。
- 便の方向は URL（`upstream` = 上り、`downstream` = 下り）と、一覧の `div.info2` の両方で取れる。今の一覧パーサーの方向判定をそのまま使う。

**Decision**: 港別ステータスと出港日時は詳細ページの `div.service > div.single` から取る。状態の対応表は一覧ページと同じものを使う。
**Rationale**: 港ごとの状態が class で構造化されているので、テキスト解析が要らない。
**Alternatives**: 一覧の便ステータスを全港に当てはめる → spec FR-004 で詳細ページを優先すると決めたので、取得失敗時の予備としてだけ残す。

## R2. マリックスライン 運航状況一覧の掲載範囲

- 2026-10-01 18時台（JST）の時点で、一覧に載っていたのは **9/30 発の上り・下りの2便だけ**。10/1 はマルエーの運航日（R4）なので、マリックスの当日便が無いことと辻褄が合う。
- 次のマリックスの運航日（10/2）の便が一覧に何時から載るかは、1日分の観測では分からない。

**Decision**: 一覧に何日先まで載るかに依存しない設計にする。載っていない日の行は、マルエーの便検索で「マリックス運航」と分かっていれば港別ページで「マリックスライン／運航予定」と表示する（spec FR-021）。掲載タイミングは実装後に運用ログ（departure_statuses の created_at）で観測する。
**Rationale**: 掲載ルールを決め打ちすると、サイトの運用が変わったときに壊れる。

## R3. マルエーフェリー 便検索

**エンドポイント**: `POST https://www.aline-ferry.com/search/result.php`

| パラメータ | 値 |
|---|---|
| `startDate` | **`YYYY年MM月DD日`**（例：`2026年10月04日`） |
| `startPort` | 出発港コード |
| `endPort` | 到着港コード |

**港コード**（トップページの `select#startPort` の option から取得）:

| 港 | コード | 港 | コード |
|---|---|---|---|
| 鹿児島 | 50 | 与論港 | 82 |
| 名瀬港 | 70 | 那覇港 | 83 |
| 亀徳港 | 78 | 本部港 | 84 |
| 和泊港 | 80 | （参考）平土野 79 / 知名 81 / 喜界 75 / 古仁屋 77 | |

**日付形式による違い（重要）**:

| startDate | 結果 |
|---|---|
| `2026-10-03`（ISO、今のスクレイパーの形式） | 日付に関係なく常に `※下記参照 / マリックスライン㈱` |
| `2026年10月03日` | `フェリー波之上 / 2026年10月3日 17:00 / 2026年10月4日 08:30 / マルエーフェリー`（亀徳→鹿児島） |

→ 今の `MarueFerry.fetch()` は ISO 形式で送っているので、`_check_service()` は実質的に常に「便あり」になっている。**今ある不具合**として、この feature で直す。

**結果テーブル**（`table.s-result tbody tr`）:

```html
<tr>
  <td><a href="../kagoshima">鹿児島航路</a></td>
  <td><a href="../kagoshima/room/ship_akebono/">フェリーあけぼの</a></td>  <!-- 他社運航の日は「※下記参照」 -->
  <td>2026年10月4日 05:50</td>   <!-- 乗船日時 = その港の出港日時 -->
  <td>2026年10月4日 19:00</td>   <!-- 下船日時 = 到着港の到着日時 -->
  <td>352km</td>
  <td>マルエーフェリー</td>        <!-- 他社運航の日は「マリックスライン㈱」 -->
  <td><form action="detail.php">…<input name="ship" value="4">…</form></td>
</tr>
```

**観測した運航パターン**（10/1 時点の検索）:

| 日付 | 下り（鹿児島→那覇） | 上り（那覇→鹿児島） | 名瀬→那覇 |
|---|---|---|---|
| 10/1 | 波之上 18:00 発 | あけぼの 07:00 発 | ※下記参照（9/30 鹿児島発のマリックス便） |
| 10/2 | ※下記参照 | ※下記参照 | — |
| 10/3 | あけぼの 18:00 発 | 波之上 07:00 発 | ※下記参照 |
| 10/4 | — | — | あけぼの 05:50 発 |

- **3日先の予定まで取れる**（10/1 の時点で 10/3・10/4 の便を確認）。
- 2社が1日おきに交互に運航していて、マルエーの船の次の便が2日後になることがある（例：波之上 10/1 18:00 鹿児島発 → 10/2 19:00 那覇着 → 次は 10/3 07:00 那覇発）。

**日数オフセット**（予備用。検索結果から確認）:
- 下り：鹿児島 +0 / 名瀬・亀徳・和泊・与論・本部 +1
- 上り：全港 +0（名瀬 21:20 発も始発当日。R1 のマリックス詳細でも同じ）

**Decision**: マルエーの出発港別の行は「出発港 × 固定の到着港 × 日付」の検索で決める。日付は `YYYY年MM月DD日` で送る。会社名の欄が「マルエーフェリー」以外の行は「他社運航」として扱う。
**Rationale**: 行の単位（出発港 × 方向 × 出港日）と、検索の単位がぴったり一致する。出港日時も公式の値が取れる。
**Alternatives**: 船ステータスを全港に当てはめる → 方向も日付も分からないので不採用（spec の clarify で議論済み）。

## R4. マルエーフェリー 船ステータスと運航状況テキスト

- **鹿児島航路ページ**（`/kagoshima/`）：`a > div.route-head > div.ferry-name` / `div.tag-list span` / `div.situation-excerpt`。`a[href]` が船別詳細ページ（`/status/route-kagoshima/ferry-akebono/21525/`）。
- **船別詳細ページ**：本文は `div.status-archive`。中身は「見出し（`h4`）→ 運航状況の本文 → **定型の注意書き** → 問い合わせ先 → 更新日」の順になっている。
- URL の末尾の数字は投稿 ID。古い ID（21524・21400）は 404 で、過去の投稿は公開されていない。WordPress REST API にもこの投稿タイプは出ていない。サイト内検索で出てくるのは「お知らせ」の記事だけで、運航状況の投稿は出てこない。**過去の異常時の実例は取れなかった。**

**定型の注意書きの問題（重要）**: 平常時でも詳細ページには次のような文が必ず入っている。

> 急激な天候変化により運航時間の遅延や変更、又は港変更や抜港(…)になることがあります。
> 徳之島で港変更がある場合、亀徳港から平土野港になります。
> 与論島で港変更がある場合、与論港から茶花港になります。

ページ全体を「港名＋抜港／港変更」で拾うと、平常時でも亀徳・和泊・与論が毎回誤判定される。

**Decision**: 港別情報の抽出は次のルールで行う。
1. 対象は `div.situation-excerpt`（鹿児島航路ページ）と、詳細ページの `h4` の後から、定型の注意書きが始まるまでの本文。区切りは `台風の影響や` を含む段落の手前とし、見つからなければ抜粋だけを使う。
2. 文（`。` と改行）単位で、港の別名（R5）と次のキーワードを探す。
   - `抜港` → 欠航
   - `港変更` / `寄港地変更` / `〜港から〜港` → 条件付（変更先の港名を詳細に残す）
   - `条件付` → 条件付
3. `場合` `ことがあります` `可能性` を含む文は、仮定の話として**除外**する。
4. どれにも当てはまらない、または判断できないときは船ステータスで表示し、`port_notice_unmatched` を warning ログに出す（spec：誤判定より取りこぼしを選ぶ）。
5. 抽出元のテキストは `operation_statuses.status_detail` と `departure_statuses.status_detail` に残しておき、後からルールを直して再解釈できるようにする（FR-012）。

**Rationale**: 実例が取れない以上、定型文に誤反応しないことを最優先にする。テストには「平常時の詳細ページ全文」を入れて、誤検出が0件になることを確認する。
**Follow-up**: 異常時の本物のページが観測できたら `scraper/tests/fixtures/` に追加してルールを直す（quickstart に手順を書く）。

## R6. タイムゾーン

- scraper コンテナは `python:3.12-slim` で TZ が未設定なので UTC で動いている（`datetime.now()` = 09:12 のとき、ホストは 18:12 JST）。
- DB の `scraped_at` も UTC のまま入っている（16:43 JST の取得が `07:43:20` で記録されている）。
- PHP は `date.timezone = Asia/Tokyo`、MySQL のセッションは `+09:00`。
- コンテナには `/usr/share/zoneinfo/Asia/Tokyo` が入っていて、`TZ=Asia/Tokyo` を付ければ JST で動くことを確認した。

**Decision**: `docker-compose.yml` の scraper サービスに `TZ: Asia/Tokyo` を設定する。コードは今の `datetime.now()` / `date.today()` のまま（naive な JST）で揃える。
**Rationale**: PHP と MySQL が naive な JST 前提なので、スクレイパーも naive な JST に揃えるのが一番変更が少ない。
**Alternatives**: aware datetime（`zoneinfo`）に全部書き換える → 変更範囲が大きく、PHP 側との受け渡しも naive なので効果が薄い。
**既存データ**: すでに入っている UTC の `scraped_at`（約100件）は直さない（spec の Out of Scope「過去データの遡及」）。画面には出していない値なので影響は無い。

## R7. 最終確認時刻と重複防止

- `BaseScraper._upsert()` は `raw_html_hash` が同じなら `continue` するので、`scraped_at` は「最後に内容が変わった時刻」になっている。
- constitution III で `raw_html_hash` による重複防止は必須。

**Decision**:
- `operation_statuses`（航路単位）は今のまま変えない。
- 新しい `departure_statuses`（港別）は行ごとに `content_hash`（ステータス・詳細・船名・時刻・運航会社から計算した SHA-256）を持つ。
  - ハッシュが同じ → `checked_at` だけ更新する
  - ハッシュが違う → 内容と `scraped_at` と `checked_at` を更新する
- 画面には `checked_at` を「○時○分時点」として出す（FR-014）。

**Rationale**: ハッシュで「変わってないものは書き換えない」を守りつつ、確認した時刻だけは毎回残せる。

## R8. マルエーの検索件数

- 行は 出発港6 × 方向2 = 12通り。今日〜3日先の4日分だと、1回の実行で48件になる。
- 30分間隔なら1日で約2,300件になり、相手サイトへの負荷として多すぎる。

**Decision**:
- 今日と明日の分（24件）は毎回取る。ステータスの判定に使うので。
- 2〜3日先の分（24件）は、前回取ってから `MARUE_FAR_SEARCH_INTERVAL_HOURS`（既定6時間）以上たったときだけ取る。前回いつ取ったかは、DB の `departure_statuses.checked_at` の最大値で判定する（新しい状態テーブルは作らない）。
- 検索の間には `MARUE_SEARCH_DELAY_SECONDS`（既定0.5秒）の待ちを入れる。
- 航路単位の便有無判定（鹿児島→那覇・那覇→鹿児島の当日分）は、港別検索の結果を使い回す。追加のリクエストはしない。

これで、平常時は1回あたり約29件（検索24件＋鹿児島航路ページ1件＋船別詳細2件＋マリックス1〜3件）、6時間に1回だけ約53件になる。

## R9. マルエーの船ステータスをどの行に当てはめるか（FR-020・021）

- 検索結果の各行から「便」を `(船名, 方向, 下船日時)` で特定できる。同じ便なら、どの出発港で検索しても下船日時（終点への到着）は同じになる。
- 船ごとに、下船日時が「今」より後の便のうち一番早いものを「まだ終わってない一番早い便」とする。
  - その便の行：船ステータスに港別情報を重ねたものを入れる
  - それより後の便の行：`status = NULL`（運航予定）
- 出港予定時刻を過ぎた行は、DB にすでに行があれば `status` と `status_detail` を更新しない（`checked_at` だけ更新）。これで、船が次の便の情報に切り替わっても、出港済みの行は書き換わらない。

## R10. 既存の航路単位レコードへの影響

- 日付形式を直すと、マリックスの日（10/2 など）はマルエーの航路単位の行も `no_service` になる。今までは毎日、船ステータスが入っていた。
- 方向ごとに検索するので、上りと下りで別々に判定できるようになる（10/1 なら両方とも「便あり」）。
- マルエーの既存テストのうち、`HTML_SEARCH_HAS_SERVICE`（作り物の船名入り）を前提にしたものは、実際の HTML 構造（会社名の列あり）に合わせて直す。
