# Feature Specification: 運航に変更がある便をメールで知らせる（V1 と同じ時刻）

**Feature Branch**: `8-schedule-change-mail`
**Created**: 2026-10-06
**Status**: Draft
**Input**: User description: "V1と同じように午前1時と午前6時と午後3時の時にスケジュールに変更があればメール飛ばして、タイトルにはV2をつけて"

## 概要

V1（リポジトリ `../ShipInfo`）は、決まった時刻に運航情報を確認し、**通常運航以外の便（欠航・遅延・条件付・運休・寄港地変更・抜港など）が1件でもあれば** 運営者へメールを送っている。
V2 でも同じ通知を出し、V1 と差し替えたあとも運営者が運航の変更をメールで把握できるようにする。

並行運用中は V1 と V2 の両方からメールが届くため、V2 のメールは件名に「V2」を入れて見分けられるようにする。

| 項目 | V1 | V2（この機能） |
|------|----|----------------|
| 確認する時刻 | 1日3回（cron `0 0,6,15`） | 1日3回：午前1時・午前6時・午後3時（日本時間） |
| 送る条件 | その回の確認で通常運航以外の便が1件以上ある | 同じ |
| 件名 | `【ShipInfo】非通常運航ステータスを検出 (N件)` | `【ShipInfo V2】非通常運航ステータスを検出 (N件)` |
| 本文 | 便ごとに会社名・運航日・方向・状況・備考 | 同じ項目（V2 は港ごとの状態もあるので港も入れる） |
| 宛先 | 設定で指定（複数可） | 同じ |
| 設定が無いとき | 送らずに警告を記録して続行 | 同じ |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 決まった時刻に運航の変更をメールで知る（Priority: P1）

運営者は、サイトを開かなくても、午前1時・午前6時・午後3時に「いま通常どおりに動いていない便」をメールで受け取り、欠航や遅延にすぐ気づける。

**Why this priority**: V1 の通知を引き継がないと、差し替えた時点で運営者が運航の変化に気づく手段が無くなる。この機能の中心。

**Independent Test**: 欠航・遅延の便があるデータを用意して確認時刻の処理を動かし、宛先に1通届くこと、本文にその便が載っていることを確かめる。通常運航だけのデータでは何も届かないことも確かめる。

**Acceptance Scenarios**:

1. **Given** 当日以降に欠航の便が1件ある、**When** 午前6時の確認が動く、**Then** 宛先に件名 `【ShipInfo V2】非通常運航ステータスを検出 (1件)` のメールが1通届き、本文に会社名・運航日・方向（または港）・状況・備考が載っている
2. **Given** 当日以降の便がすべて通常運航、**When** 確認が動く、**Then** メールは送られない
3. **Given** 欠航・遅延・条件付の便が合わせて3件ある、**When** 確認が動く、**Then** 3件すべてを1通にまとめて送り、件名の件数は 3 になる
4. **Given** 午前6時に欠航を知らせた便が、午後3時になっても欠航のまま、**When** 午後3時の確認が動く、**Then** その便を含むメールがもう一度届く（V1 と同じ）
5. **Given** 午前1時・午前6時・午後3時以外の時刻、**When** 運航情報が更新されて欠航が増えても、**Then** その時点ではメールは送られない（次の確認時刻にまとめて知らせる）

---

### User Story 2 - V1 と V2 のメールを見分けられる（Priority: P1）

並行運用中、運営者は V1 と V2 の両方からメールを受け取る。件名を見ただけで V2 からのメールだと分かり、両者の内容を比べて V2 が正しく動いているか確かめられる。

**Why this priority**: 差し替え前の検証に必須。件名で区別できないと、どちらのシステムの通知か分からず比べられない。

**Independent Test**: V2 から送られたメールの件名に「V2」が入っていることを確かめる。

**Acceptance Scenarios**:

1. **Given** V2 から通知が送られた、**When** 受信箱で件名を見る、**Then** 件名は `【ShipInfo V2】` で始まり、V1 の `【ShipInfo】` と見分けられる

---

### User Story 3 - メールの設定が無い・送れなくても運航情報の収集は止まらない（Priority: P2）

開発環境やメール設定が済んでいない環境でも、運航情報の収集・サイト表示はいつもどおり動く。送信に失敗したときは、運営者があとから原因を追える記録が残る。

**Why this priority**: 通知は付加機能。通知の不具合でサイトの情報が古くなるほうが利用者への影響が大きい。

**Independent Test**: 送信先の設定を空にして確認時刻の処理を動かし、警告が記録され、収集処理が止まらないことを確かめる。送信先サーバーに繋がらない設定でも同様に確かめる。

**Acceptance Scenarios**:

1. **Given** 送信先・送信元・送信サーバーのどれかが設定されていない、**When** 確認が動く、**Then** メールは送らず、「設定が無いので送らなかった」旨の警告が記録され、収集は続く
2. **Given** 送信サーバーに繋がらない、**When** 確認が動く、**Then** 失敗が記録され、収集は続く。失敗した通知は次の確認時刻まで再送しない

---

### Edge Cases

- 確認時刻にシステムが止まっていた（再起動中など）→ その回は送らない。あとから遅れて送ることはしない（次の確認時刻で最新の状態を送る）
- 同じ確認時刻に処理が2回動いてしまう（再起動の直後など）→ 同じ確認時刻のメールは1通だけにする
- 過去の日付の便（運航日が当日より前）→ 対象にしない
- 運航状況が「不明」の便 → V1 と同じく通常運航以外として載せる
- 「便無し」（もともと便が設定されていない日）→ 変更ではないので載せない
- 同じ便が航路単位の状態と港ごとの状態の両方で通常以外になっている → 本文で同じ便が重複して見えないよう、まとめて1件として載せる
- 宛先が複数（カンマ区切り）→ 全員に同じメールを1通ずつ届ける。空白や空の宛先は無視する
- 1社のスクレイピングが失敗していて情報が古い → その会社は最後に取れた状態で判定する（取れていない旨は本文に書かない。収集の失敗は既存の実行ログで追う）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは日本時間の毎日 1:00・6:00・15:00 に、当日以降の運航状況を確認しなければならない
- **FR-002**: 確認時点で通常運航以外の便（欠航・遅延・条件付・運休・寄港地変更・抜港・不明など）が1件以上あれば、設定された宛先へメールを1通送らなければならない。0件なら送ってはならない
- **FR-003**: 「通常運航以外」の判定は、サイトに表示している状態と一致しなければならない（サイトで通常運航と出ている便を通知に載せない／その逆もしない）。「便無し」は通知に載せない
- **FR-004**: 前回の確認と同じ内容でも、通常運航以外の便があれば毎回送らなければならない（V1 と同じ）
- **FR-005**: 件名は `【ShipInfo V2】非通常運航ステータスを検出 (N件)` とし、N はその回のメールに載せた便の件数でなければならない
- **FR-006**: 本文には便ごとに、会社名・運航日・方向または港・状況・備考（あるとき）を載せなければならない。並びは会社名→運航日の順とする
- **FR-007**: 宛先・送信元・送信サーバーの情報は、コードではなく環境ごとの設定で指定できなければならない。宛先は複数指定できなければならない
- **FR-008**: 設定が足りないとき、または送信に失敗したときは、送らずに（失敗として）記録を残し、運航情報の収集・サイト表示に影響を与えてはならない
- **FR-009**: 同じ確認時刻（同じ日の同じ時刻枠）について、メールを2通以上送ってはならない
- **FR-010**: 確認時刻を逃した回（その時刻にシステムが止まっていたなど）を、あとから遅れて送ってはならない
- **FR-011**: 開発環境では、実際の宛先に届かずに送った内容を確かめられなければならない

### Key Entities

- **通知の確認回**: 日付と時刻枠（1:00・6:00・15:00）で1回を表す。その回に送ったか・何件だったか・失敗したかを持ち、同じ回の二重送信を防ぐのに使う
- **通知に載せる便**: 既存の運航状況（航路×日付）と港ごとの状況（航路×港×出港日×船）のうち、当日以降で通常運航以外のもの。新しい履歴は持たず、確認時点の最新状態をそのまま使う（Constitution III）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 通常運航以外の便がある日は、1:00・6:00・15:00 の各回の後 5 分以内に宛先へメールが届く
- **SC-002**: 通常運航だけの回にメールが届く誤通知は 0 件
- **SC-003**: 同じ確認回のメールが 2 通以上届くことは 0 件
- **SC-004**: 並行運用の 1 週間で、V1 と V2 の同じ回のメールを比べたとき、V1 に載っていて V2 に載っていない便が 0 件（V2 にしかない港ごとの情報は差として許容する）
- **SC-005**: メール設定が無い・送信に失敗した場合でも、サイトの運航情報の更新が止まった回数は 0 回
- **SC-006**: 運営者は件名だけで V1 と V2 のメールを 100% 見分けられる

## Assumptions

- 「スケジュールに変更があれば」は V1 と同じく「確認時点で通常運航以外の便があれば（前回と同じ内容でも）毎回送る」と解釈する
- 確認時刻は 1:00・6:00・15:00（日本時間）。V1 の cron は `0 0,6,15` だが、0 時ではなく 1 時にすることをユーザーと確認済み（2026-10-06）
- V1 は会社ごとに1通ずつ送っていたが、V2 は1回の確認で全社分を1通にまとめる（届く通数を減らし、比べやすくするため）
- V2 は運航情報を30分ごとに取っているので、通知は収集とは別に、確認時刻にその時点の最新状態を見て判定する（V1 のように「収集の直後に送る」形にはしない）
- 対象は当日以降の便。当日の「当日」は日本時間で判定する
- 送信には既存の SMTP サーバー（V1 と同じもの）を使い、宛先・送信元も V1 と同じものを本番の設定に入れる
- メールは本文のみのテキスト形式（V1 と同じ）。HTML メールやサイトへのリンクはこの機能の範囲外
- 利用者（一般の閲覧者）向けのメール配信・購読機能は範囲外。宛先は運営者のみ
- 「前回から変わった便だけ送る」差分通知は範囲外（必要になったら、変更履歴の保持期間とあわせて別機能で設計する）

## Out of Scope

- 一般利用者向けのメール購読・LINE・プッシュ通知
- 前回の確認との差分だけを送る通知
- 確認時刻を画面から変更する機能
- V1 の通知を止める作業（差し替え時に別途行う）
