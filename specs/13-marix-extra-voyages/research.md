# Research: マリックスラインの臨時便を港別ステータスに出す

**Date**: 2026-10-26 | **Spec**: [spec.md](spec.md)

## R1. 便の種類の見分け方（FR-001）

**Decision**: 一覧の便（`div.status_single_cover`）ごとに、種類を3つのどれかに決める（`_voyage_kind(block, detail_html) -> "extra" | "regular" | "unknown"`）。

| 条件（上から順に見る） | 種類 |
|---|---|
| 一覧の便のクラスに `temporary` がある | `extra`（臨時便） |
| 詳細ページが取れて、見出し（`h1.heading1`）に `【臨時便` があるか、寄る港（`no_status` 以外の `div.service > div.single`）の**全部**のクラスに `temporary` がある | `extra` |
| 詳細ページが取れて、上のどちらも無い | `regular`（定期便） |
| `fetch()` で詳細ページを取りに行って取れなかった（`_detail_pages[url]` が None） | `unknown`（分からない） |
| `fetch()` を通っていない（`_detail_pages` が無い。既存のテストの呼び方） | `regular`（今までどおり） |

**Rationale**:
- 詳細ページの見出し・港の `temporary` は、2026-08〜09 の臨時便4例（`samples/`）のすべてにある。定期便の詳細ページには無い
- 一覧の `temporary` は一覧の CSS（`.up_stream_services .temporary`・`.down_stream_services .temporary{order:3}`）からの推測で、実物は未確認。外れても詳細ページで見分けられる
- 港の `temporary` は全部の港に付くときだけ。定期便が1港に臨時寄港しただけで便ごと臨時便にしない（PR #90 レビュー。臨時寄港が同じクラスで出るかは未確認）。`temporary` は状態ではなく便の種類なので、`_STATUS_BY_CLASS` には入れず、港の状態は `temporary` 以外のクラスで決める。ほかの状態のクラスが無ければ `extra`、あれば（`temporary cancel alert` など）その状態。定期便（1港だけ `temporary`）の港は、ほかの状態のクラスが無ければ `operating`（`extra` で書くと、次の回の欠航が臨時便の行として守られて出なくなる）。`temporary alert`（`alert` だけ）は `extra`（一覧の `alert` だけは `cancelled` だが、`temporary` と一緒のときは臨時便を優先。詳細ページの港で `alert` だけの例は未確認）
- 見出しの書き方は「【臨時便】」「【臨時便運航】」「【臨時便・航行経路変更】」の3つがあった。前方一致（`【臨時便`）なら全部拾える
- 詳細ページが取れないときに一覧のクラスだけで「定期便」と決めると、臨時便（一覧のクラスが `route alert` など読めるもの）が航路単位を書き、予備ルートの行も全港に入る（PR #89 レビュー）。分からないものは「分からない」として扱う（R6・R8）
- 既存のテスト（`test_normal_down_delayed_up` など）は `parse(fetch())` を呼ぶが、詳細ページをモックしていない。`responses` が接続エラーを出すので、これらの便は全部 `unknown` になる。航路単位の扱い（R8）は、このとき今までどおりの結果になるようにする

**Alternatives considered**:
- 詳細ページの URL（定期便は `/service/downstream20260906/`、臨時便は `/service/service6727/`）で見分ける → 公式が URL の付け方を決めているとは限らない。投稿の ID の形なので、ほかの告知で同じ形が出ることもありうる。採らない
- 一覧のクラスだけで見分ける → 実物が未確認。外れると、臨時便が「不明」のまま航路単位を上書きする今の問題が残る

## R2. 方向の決め方（FR-009）

**Decision**: 次の順に決め、最初に決まったものを使う。

1. 見出し（`div.info2`）の始発港：「鹿児島…発」→ 下り、「那覇…発」→ 上り（今のまま）
2. 一覧の欄：`div.down_stream_services` の中 → 下り、`div.up_stream_services` の中 → 上り
3. 見出しの行き先：「那覇… 向け」→ 下り、「鹿児島… 向け」→ 上り

どれでも決まらなければ、今までどおり `direction_unknown` を出して読み飛ばす。

**Rationale**:
- 9/27・8/24 の臨時便は「名瀬港発 鹿児島新港向け」。1 では決まらない
- 一覧は上り・下りの欄に分かれている（2026-10-26 の一覧で確認）。臨時便も CSS に上り・下りそれぞれの指定がある
- 欄の作りが変わったときのために、行き先を最後の手がかりにする
- 1 を先にするのは、今の定期便の結果を変えないため（FR-013）

**Alternatives considered**:
- 欄だけで決める → 今のテストの一覧の HTML（`HTML_NORMAL_DOWN_DELAYED_UP` など）には欄が無い。今の結果を変えないために 1 を残す
- 詳細ページの見出しの「上り便」「下り便」で決める → 詳細ページが取れないと決まらない

## R3. 臨時便の港の行（FR-002〜FR-004）

**Decision**: 臨時便の詳細ページの港は次のように扱う。

| 港のクラス | 行 |
|---|---|
| `temporary` | 「臨時便」（`extra`） |
| `no_status`（「―」「寄港しません」） | **作らない**。時刻も使わない |
| `cancel`・`conditional` など今の語彙 | 今の対応どおり（臨時便そのものの欠航など） |
| 知らないクラス | 「不明」（今までどおり。`detail_status_unknown`） |

- `_STATUS_BY_CLASS` に `"temporary": OperationStatusEnum.extra` を足す
- 臨時便は、一覧のクラスに関係なく便全体の状態（`voyage_status`）を `extra` として `_departures_from_detail()` に渡す。関数の中では `voyage_status == OperationStatusEnum.extra` で臨時便かを決める（引数を増やさない。PR #89 レビュー）。見出しの h2（「航行経路を「那覇 → 名瀬→鹿児島」に変更し運航」）も、`with_notes` でそのまま詳細に入る
- 出港予定・到着予定（終点の入港）・船名・詳細（見出しの h4・h2 と港の `div.exp`）は、今の `_departures_from_detail()` と同じく詳細ページから決める
- 航路の寄港順のうち、詳細ページに無い港（`detail_stop_missing`）は、臨時便では警告を出さない。寄らない港は `no_status` として載っているので、これは起きない想定

**Rationale**:
- 9/6・9/27 の臨時便では、`no_status` の港に定期便の時刻や別の日付（9/27 の便に「08月25日」）が残っている。今の作りだと 2027-08-25 の「抜港」の行ができる
- 12 と同じく「寄らない港には臨時便が無い」とする（Clarifications）

## R4. 同じキーに定期便と臨時便が来たとき：同じ回（FR-005・FR-006）

**Decision**: `parse_departures()` の最後で、同じキー（航路・港・出港日・船名）の行を1本に絞る（`_resolve_extra_conflicts()`）。

| 定期便のその港の状態 | 残す行 |
|---|---|
| 欠航・運休・抜港・不明 | 臨時便の行 |
| それ以外（通常運航・条件付・航行経路変更） | 定期便の行。詳細の後ろに「（臨時便 HH:MM発あり）」を足し、警告 `extra_voyage_conflict` |

- 一覧の並び順に関係なく、同じ結果になる
- 臨時便同士・定期便同士で同じキーになったときは、今までどおり先の行（Base が `departure_duplicate_key` を出す）

**Rationale**:
- Base の `_upsert_departures()` は、同じキーの2本目を捨てる。並び順で結果が変わるのはこのため
- Base で優先を決めると、会社ごとの決まり（臨時便の見分け方）が Base に入る（原則 I）。マリックスラインの中で絞る
- 定期便が走る日に同じ船で臨時便も出る例は、公式の記録に無い。12 の R7 と同じ扱いにして、警告で気づけるようにする

## R5. 前の回に臨時便が書いた行（FR-007）

**Decision**: 定期便の行（欠航・運休・抜港・不明のもの）と同じキーに、この回の臨時便の行が無く、DB に状態 `extra` の行があるときは、次のどちらかなら定期便の行を書かない（DB の臨時便の行を残す）。

1. その行の `source_url`（臨時便の詳細ページ）が今回の一覧にあるのに、詳細ページを読めていない（種類が `unknown`、または `extra` で詳細ページが取れなかった）
2. その臨時便が出港済み。DB の `extra` の行のうち、同じ `source_url` の行の出港予定（`scheduled_departure_at`）のいちばん早いもの（始発港の出港）が今以前。港の行ごとには見ない

どちらでもなければ、定期便の行を書く。

- 臨時便が一覧から消えて、まだ出港していない → 取りやめとみて、定期便の欠航に戻す。同じキーの定期便が無いときも、その URL の `extra` の行を消す（`_upsert_departures()`。PR #90 レビュー）
- 臨時便を読めて、もうそのキーを書かない（出港日がずれた）→ 定期便の行に戻す（R7）

`_extra_rows_kept()` で、マリックスラインの航路の `status = 'extra'` の行（キー → `source_url`）を、`parse_departures()` の頭で1回だけ読む。範囲は、出港日が一覧の便の始発日のいちばん前（一覧に便が無ければ今日）以降。

2 の「いちばん早い出港予定」は、この範囲で絞らない。`_extra_first_departures()` で、`_extra_rows_kept()` に出た `source_url` ごとに、`status = 'extra'` の行の `MIN(scheduled_departure_at)` を出港日の範囲なしで読む（1回の `GROUP BY source_url`）。

**Rationale**:
- 9/7 の後、臨時便が出港してから一覧から先に消え、定期便（欠航）だけが残る回がありうる。そのとき欠航で上書きすると、出港した臨時便が「欠航」に戻る（2）
- 出港済みを港の行ごとに見ると、那覇 07:00 を出た後に一覧から消えた回に、那覇は「臨時便」のまま、まだ寄っていない名瀬（21:20）だけ「欠航」に戻る。同じ便なので、12 と同じく便ごと（始発港の出港）で決める
- 鹿児島発・名瀬発の便は、ほとんどが日をまたぐ（鹿児島 18:00 発 → 名瀬は翌朝）。始発港の行は、途中の港の行より前の出港日になる。範囲の中だけでいちばん早い出港予定を取ると、臨時便の始発日が一覧の便の始発日より前のとき（台風を避けて前の日に出したときなど）に始発港の行が範囲から外れる。そうなると、途中の港の時刻で「まだ出港していない」とみて、まだ寄っていない港だけ「欠航」に戻る。URL ごとに範囲なしで取れば、一覧の日付に関係なく始発港の出港で決まる（PR #89 レビュー）
- 詳細ページが一度取れなかっただけで、臨時便を欠航に戻したくない（1）
- 一覧から消えた未出港の臨時便まで守ると、取りやめになった臨時便の「臨時便」が、その日が過ぎるまで出続ける。定期便の欠航で上書きされないので、気づけるのはログだけになる（PR #89 レビュー）
- 「臨時便から書いた行」の目印は状態 `extra` にする。マリックスラインの行はどれも詳細ページの URL を `source_url` に持つので、12 のように URL では見分けられない。臨時便そのものが欠航した行（`cancelled`）は、定期便の欠航で上書きされても状態は同じなので困らない

**制約（PR #90 レビュー）**: `_extra_first_departures()` は状態 `extra` の行だけを見る。始発港で定期便が R4 に勝つと（臨時便の行が落ちる）始発港の `extra` の行が無くなり、いちばん早い時刻が途中の港の時刻になる。その間に臨時便が一覧から消えると、出港済みでも未出港とみなされて途中の港が定期便の欠航で上書きされる。起きる条件が狭いので受け入れる。

出港予定が全部 NULL の臨時便は、いちばん早い出港日が今日より後なら未出港、今日以前なら出港済みかもしれないとみる（時刻が取れない行はほぼ無いが、取りやめの行が残り続けないように）。

**Alternatives considered**:
- `source_url` の形（`/service/service\d+/`）で見分ける → R1 と同じ理由で採らない
- 列を足す（臨時便の印）→ マイグレーションが要る。状態 `extra` で足りる
- 一覧に無い臨時便の行は全部守らない → 出港済みの臨時便が「欠航」に戻る

## R6. 予備ルート（FR-010・FR-015）

**Decision**:
- 種類が `extra` で詳細ページが取れなければ、予備ルート（`_fallback_departures()`）を使わない。警告 `extra_voyage_detail_missing` を出す。前回の行は触らない
- 種類が `unknown`（詳細ページが取れず、一覧に `temporary` が無い）は、今までどおり予備ルートの行（船名なし）を作る。臨時便だった場合は、次に詳細ページを読めた回に R7 の後始末で消える
- 定期便の予備ルートの行は、臨時便の行と同じ港・日付でも今までどおり作る（PR #89 レビュー。Clarifications）。船名なしの行と臨時便の行が並ぶのは定期便の詳細ページが取れない回だけで、次に取れた回に今の `replace_source`（#28）で船名なしの行は消える

**Rationale**:
- 予備ルートは便全体の状態を全港に当てはめる。臨時便は寄る港が詳細ページにしか無いので、当てはめると寄らない港に行ができる
- 予備ルートの行は、定期便の詳細ページが一度も読めていないときだけできるので、船名が分からない。臨時便と同じ船かどうか決められないので、(航路, 港, 出港日) で抑えたり消したりすると、9/6 のように同じ日・同じ港を出る別の船（プラス）の行まで消える

**Alternatives considered**:
- 一覧の「過去の運航状況」の欄から便の船名を引き、同じ船だけ抑える → 先の日の便がその欄に出るか確かめられていない。並ぶのは一時的なので、前提を増やしてまでやらない

## R7. 臨時便の行の後始末（FR-011）

**Decision**: Base のルール6（`replace_source`）で消す。臨時便の行の `replace_source` は `(None, None, source_url)`（航路・港を決めない。方向が前の回と変わっても前の航路の行が消える。PR #93 レビュー）にして、`source_url` がその URL の行のうち、この回にその臨時便が書かなかったキーの行を消す。はじめは `MarixLine._upsert_departures()` を上書きして同じことをしていたが、flush の順番などを2か所で合わせ続けることになるので Base に寄せた（#91）

- 出港日がずれた古い日付の行、寄らなくなった港の行（前は寄る予定だった港が `no_status` になった）、種類が `unknown` だった回の予備ルートの行（船名なし）が消える
- R4・R5 で落とした行は Base に届かないので、そのままだと前の回の予備ルートの行（船名なし・定期便の URL）が、臨時便が勝った港に残る。落とした行の `replace_source` は、`self.unwritten_sources`（書いたキーが無いものとして扱う）で Base に渡す。落とした行のキーの行は、勝った便の行で上書きされて `source_url` が変わっている（R5 で残した行はもとから臨時便の URL）ので、消す対象にならない。内容のハッシュが同じでも Base は `source_url` を書き換える（PR #93 レビュー）
- 出港前に一覧から消えた臨時便（取りやめ）は、`MarixLine._upsert_departures()` で、その URL の `extra` の行だけ消す。出港済みか（R5）を見たのは `extra` の行だけなので、ほかの状態の行は消さない
- 消す前に `session.flush()` する（Base。下の R10）

**Rationale**:
- Base の `replace_source` は、その回に書いた港の分しか登録されない。臨時便は `no_status` の港を書かないので、寄らなくなった港の古い行が残る（PR #89 レビュー）。定期便なら `no_status` の港は抜港の行で上書きされるので、これは臨時便だけの穴
- 臨時便が上書きした行（もとは定期便の行）は、出港日がずれた回に、同じ回の定期便の行（R5）で上書きされて `source_url` が定期便の URL に変わる。flush の後なら、後始末の対象にならない

## R8. 航路単位（FR-008）

**Decision**: `parse()` で、便の種類（R1）ごとに扱いを変える。

| 種類 | 航路単位の行 | `seen` |
|---|---|---|
| `regular` | 今までどおり | 今までどおり入れる |
| `extra` | 作らない | 入れない（同じ日の定期便を捨てないため） |
| `unknown`・一覧のクラスが状態として読める | **控えの行**：同じ航路・日付に `regular` の便が無いときだけ、一覧のクラスで今までどおり書く | 書いたときに入れる（ループの後） |
| `unknown`・一覧のクラスが状態として読めない | 作らない。警告 `voyage_kind_unknown`（url） | ループの最後にまとめて入れる |

- 控えの行と読めない便は、ループの中では書かず、`seen` にも入れない。ループの後、`regular` で埋まらなかった航路・日付だけ、控えの行（一覧の順で最初のもの）を書いて `seen` に入れる。読めない便のキーは、そのあと `seen` に入れる
- 控えの行を書くので、詳細ページが一時的に取れない回も、1方向1便の普通の日は今までどおり航路単位が書かれる（既存のテストもこの形。R1）
- 臨時便（一覧のクラスが `route alert` などで読めて、詳細ページが取れない）が一覧で先に来ても、同じ日の定期便が後ろにあれば定期便で書く（PR #89 レビュー）
- 読めない便を `seen` に入れないと、その方向の今日の便がそれだけのときに `no_service`（便なし）を書いてしまう。実際には船は出ているかもしれない（PR #89 レビュー）。読めない便から「不明」を書かないのは、一覧の HTML が変わるまで直らないため（下）
- 残る穴：臨時便しか無い日に、一覧に `temporary` が無く、一覧のクラスが読めて、詳細ページも取れない回は、臨時便の一覧のクラスで航路単位が書かれ、一覧の HTML が変わるまで残る。一覧には `temporary` が付くと考えている（CSS）ので、3つが重なるのはまれとみて受け入れる
- 臨時便しか無い日は、今日なら今までどおり `no_service`（便なし）
- 一覧に `temporary` が付かず（R1 は未確認）詳細ページも取れない回は、その日に定期便が無いと一覧のクラスがそのまま控えの行になり、「通常運航」などと出る（FR-014 の「便なし＋臨時便」のバッジにならない）。一覧の `temporary` の実物を確かめるまでの一時的な穴として受け入れる
- `parse()` も `fetch()` で取った `self._detail_pages` を見る（R1）

**Rationale**:
- 今は同じ航路・日付の最初の便を使うので、臨時便が先だと「不明」になる
- `operation_statuses.status` は ENUM で `extra` を持たない。臨時便を航路単位に書くと、DB で落ちる
- `_upsert()` は、同じ航路・日付の行の `raw_html_hash` が今回と同じなら書き直さない。分からない便から航路単位を書くと、一覧の HTML が変わるまで直らない。書かなければ、詳細ページが取れた回に（行が無いか、前の一覧のハッシュなので）書かれる
- 定期便の詳細ページが一時的に取れない回も、一覧のクラスが読めれば控えの行として今までどおり書かれる。読めないときだけ、その回は書かれない（前回の行が残る）

## R9. トップの会社カードのバッジ（FR-014）

**Decision**: `StatusController::routesDepartingMidway()` で、航路単位が `no_service` の航路について、今日その方向に臨時便以外の便の行が1つも無く（始発港の行も見る）、`PortBoardDay::firstExtraDepartureOf()` が臨時便を返すときは、`['kind' => 'badge', 'state' => null, 'status' => Extra]` にする。それ以外は今までどおり `midwayDisplay()`。

- 臨時便以外の便の行があるかは、`PortBoardDay::hasRegularDeparturesOf(companyId, direction)`（新規。全部の行のうち、状態が Extra でない出発の entry があるか）で見る
- 途中の港を出る定期便があるときは、今までどおり `midwayDisplay()` の結果（12 の FR-016）
- 始発港に臨時便以外の行（予備ルートの行など）があるときも、今までどおり。状態の分からない定期便を「臨時便」のバッジで隠さない（PR #89 レビュー）
- 会社を問わない。マルエーフェリーの「鹿児島 16:00 発の臨時便しか無い日」も「臨時便」になる

**Rationale**:
- 航路単位が `no_service` のときのバッジは `routesDepartingMidway()` で決めている。ここに1つ条件を足すのがいちばん小さい
- `midwayDeparturesOf()` は始発港の行を見ないので、始発港を出る臨時便（8/27 の鹿児島 10:00）を拾えない。`firstExtraDepartureOf()` は始発港の行も見るので、これを使う
- 会社が「本日運航なし」に入るかは `hasDeparturesOf()` で決めていて、始発港の行も見ている。臨時便があれば会社カードは出る（今のまま）

## R10. Base の flush

**Decision**: `BaseScraper._upsert_departures()` で、行の書き込みが終わった後、ルール5（`replace_scope`）・ルール6（`replace_source`）で消す前に `self.session.flush()` を入れる。臨時便の後始末（R7）も同じルール6なので、この flush の後に消える（#91）。取りやめた臨時便の行は `MarixLine._upsert_departures()` が Base の後に消すので、この flush の後になる。

**Rationale**:
- 本番の `SessionLocal` は `autoflush=False`（`scraper/scraper/db/connection.py`）。flush しないと、消す行を探す SELECT は DB に残った古い `source_url` を読む。さっき定期便の行で上書きした行（メモリの中だけで `source_url` が変わった行）を消してしまう（PR #89 レビュー）
- テストの `db_session` は `sessionmaker` の既定（`autoflush=True`）なので、このバグが見えない。`db_session` を一律で `autoflush=False` にすると、既存のテスト（`test_base_departures.py` など。行を足した後に同じキーを読む）が落ちる。一律の切り替えはこの機能の範囲外にして、この流れを確かめるテストだけ `db_session.autoflush = False` にする
- flush は commit のときにどのみち行われる書き込みを前に出すだけで、ほかの会社の結果は変わらない
