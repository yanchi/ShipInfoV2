# Feature Specification: スクレイパーを振る舞いを変えずに整理する

**Feature Branch**: `17-scraper-refactor`
**Created**: 2026-11-02
**Status**: Draft
**Input**: User description: "17-scraper-refactor: スクレイパーのリファクタリング（振る舞いは変えない）。(1) marue_ferry.py と marix_line.py で重複している _load_routes・_load_stops などの共通処理を BaseScraper か utils に寄せる。(2) 1788 行ある marue_ferry.py を検索（_search・_match_voyage）・臨時便（_build_extra_voyage・_extra_records・抜港フラグ）・parse_departures などの責務ごとにパッケージ分割する。外から見たクラス名 MarueFerry と SCRAPER_REGISTRY は変えない。(3) 臨時便ロジックで両社に共通する部分（重複解決・取り下げ便の削除）が見えたら共通化する。ただし無理な抽象化はしない。既存の pytest はすべてそのまま通ること、DB に書く内容が変わらないこと。"

## 概要

スクレイパーは仕様 2・9・11・12・13・15・16 を重ねて大きくなった。2026-11-02 時点の形：

| 場所 | 行数 | 起きていること |
|---|---|---|
| マルエーフェリー | 1788 行・1 クラス・メソッド約 60 | 一覧・便検索・船の詳細・臨時便・抜港・DB 書き込みが1か所。スクレイパーのコードの約 2 割、変更回数も最多（40 回） |
| マリックスライン | 892 行 | 臨時便の重複解決（約 90 行）・詳細ページの読み取り（約 120 行）が長い |
| 両社 | — | 航路・寄港順の読み込みが同じコードで2つある。臨時便の「残す行・ぶつかった行・取り下げた行」の扱いも似た処理を別々に持つ |

このまま 3 社目や臨時便の仕様変更を足すと、同じ処理のコピーがもう1つ増え、直し漏れが起きる。

この機能では、**利用者・運用から見た振る舞いを1つも変えずに**、コードの置き場所と重複だけを整理する。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 両社で同じ処理を1か所にする (Priority: P1)

開発者が、航路・寄港順の読み込みなど両社で同じことをしている処理を、共通の場所で1回だけ直せる。

**Why this priority**: いちばん小さく安全で、すぐ効く。US2・US3 の土台にもなる（分割の前に重複を減らしておくと、分けるコードが減る）。

**Independent Test**: 共通にした処理を両社が使っていて、各社のファイルに同じ中身の処理が残っていないこと。既存のテストが全部通ること。

**Acceptance Scenarios**:

1. **Given** 両社のスクレイパーに同じ中身の処理（航路の読み込み・寄港順の読み込み）がある, **When** 整理する, **Then** その処理は共通の場所に1つだけあり、両社はそれを使う
2. **Given** 会社ごとに違うところ（始発港の名前・港コードの対応など）がある, **When** 整理する, **Then** 違うところは各社に残し、無理に1つにしない

---

### User Story 2 - マルエーフェリーを役割ごとに分ける (Priority: P1)

開発者が、マルエーフェリーの「便検索」「臨時便」「港別の行づくり」などを、それぞれ別のファイルで読んで直せる。1つの仕様の変更で、関係ない役割のコードを開かなくて済む。

**Why this priority**: 負債がいちばんたまっている場所。次にマルエーの仕様を変えるときの読み違い・直し漏れを減らす。

**Independent Test**: マルエーフェリーのコードが役割ごとの複数のファイルに分かれていて、どのファイルも目安の行数以内であること。スクレイパーの登録・呼び出し方は変わらず、既存のテストが全部通ること。

**Acceptance Scenarios**:

1. **Given** マルエーフェリーのコードが1ファイルにある, **When** 整理する, **Then** 少なくとも「一覧の取得と読み取り」「便検索と便の突き合わせ」「臨時便（抜港のフラグを含む）」「港別の行づくりと DB 書き込み」が別のファイルになる
2. **Given** スクレイパーの登録（会社とクラス名の対応）と、`ferry_companies` の `scraper_class` の値, **When** 整理する, **Then** どちらも変えずにマルエーフェリーが動く
3. **Given** ほかのコード・テストが使っているマルエーフェリーの名前（クラス・定数・臨時便のデータの型）, **When** 整理する, **Then** 今までと同じ場所から読み込める

---

### User Story 3 - 臨時便の扱いで両社に共通するところをまとめる (Priority: P2)

開発者が、臨時便の行の「前回から残す行」「定期便とぶつかった行」「公式から消えた行を消す」の決まりを、両社で同じなら1か所で直せる。

**Why this priority**: 共通にする価値はあるが、両社で決まり（12・13 の仕様）が少しずつ違う。違いを消すと振る舞いが変わるので、US1・US2 のあとで本当に同じ部分だけをまとめる。

**Independent Test**: まとめた処理について、両社のテストがそのまま通ること。まとめなかった部分は、なぜ分けたままにしたかが plan か research に書いてあること。

**Acceptance Scenarios**:

1. **Given** 両社で同じ決まりの臨時便の処理がある, **When** 整理する, **Then** 1か所にまとめ、両社がそれを使う
2. **Given** 会社ごとに決まりが違う臨時便の処理がある（12 と 13 で決め方が違うもの）, **When** 整理する, **Then** まとめずに各社に残し、違いを書き残す
3. **Given** まとめるために会社ごとの分岐・設定を3つ以上足さないといけない, **When** 判断する, **Then** まとめない（無理な抽象化をしない）

---

### Edge Cases

- **テストが中の名前を直接使っている**：テストはマルエーの中の処理・日付・待ち時間・設定を、ファイルの場所を指定して差し替えている。分けたあとは、差し替える場所（import 先・patch 先）だけは新しい場所に直してよい。期待値・入力・テストの数は変えない
- **前回のスクレイプと同じ公式ページ**：分けたあとも同じページなら「変更なし」と判断され、行を書き直さない（重複防止のハッシュの作り方を変えない）
- **ログ**：運用で見るログの出来事の名前・項目（警告・臨時便のぶつかりなど）は変えない
- **途中で失敗したとき**：例外の種類・どこまで書いて止まるか・スクレイパーログに残る内容は変えない
- **整理の途中の状態**：どの段階（US1 だけ・US2 まで）で止めても、テストは通り、動くこと

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 同じ公式ページ（テストの固定ページ）を読んだとき、整理の前後で DB に書く行（会社の運航状況・港別の行・スクレイパーログ）の中身が同じでなければならない。重複防止のハッシュの値も同じでなければならない
- **FR-002**: 既存のスクレイパーのテストは、期待値・入力・テストの数を変えずに全部通らなければならない。直してよいのは、読み込む場所・差し替える場所（中のファイル名）だけ
- **FR-003**: スクレイパーの登録（会社とクラス名の対応）、クラス名 `MarueFerry`・`MarixLine`、外から読み込んでいる名前（定数・臨時便のデータの型）は、今までと同じ書き方で使えなければならない
- **FR-004**: 両社で中身が同じ処理（少なくとも航路の読み込み・寄港順の読み込み）は、共通の場所に1つだけ置かなければならない
- **FR-005**: マルエーフェリーのコードは、役割ごと（少なくとも US2 の4つ）の複数のファイルに分けなければならない。1ファイルの目安は 600 行以内とする
- **FR-006**: 臨時便の処理は、両社で決まりが同じ部分だけをまとめなければならない。決まりが違う部分はまとめず、違いを plan か research に書き残さなければならない
- **FR-007**: ログの出来事の名前と項目、例外の種類、スクレイパーログの内容を変えてはならない
- **FR-008**: 新しい機能・バグ直し・仕様の変更を混ぜてはならない。整理中に見つけたバグは、この機能では直さず別の Issue にする
- **FR-009**: lint・フォーマット・スキーマの確認（`make lint-scraper`・`make check-schema`）が、整理の前と同じく通らなければならない
- **FR-010**: 作業は US1 → US2 → US3 の順に、それぞれ単独でテストが通る区切りでコミットしなければならない

### Key Entities

- **スクレイパー**（既存）：会社ごとに公式ページを読み、DB に書く。登録された名前で呼び出される
- **港別の行・会社の運航状況・スクレイパーログ**（既存）：スクレイパーが書くもの。この機能では中身を変えない

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 既存のスクレイパーのテスト（2026-11-02 時点でテスト関数 278 個）が、期待値を変えずに全部通る
- **SC-002**: 同じ固定ページで両社を1回ずつ流したとき、整理の前後で DB の行が1行も違わない
- **SC-003**: マルエーフェリーのコードのうち、いちばん大きいファイルが 600 行以内（今は 1788 行）
- **SC-004**: 航路・寄港順の読み込みが、スクレイパーのコード全体で1か所ずつになる（今は2か所ずつ）
- **SC-005**: 本番に出したあとの最初の定期スクレイプで、公式ページが変わっていない会社の行の更新時刻が進まない

## Assumptions

- 「既存の pytest はそのまま通る」は、テストの期待値・入力・件数を変えないこととする。テストは中のファイルの場所を指定して日付・待ち時間・設定を差し替えているので、ファイルを分けると差し替え先だけは直す必要がある（直さずに済む形にできるならそれでよい）
- 「DB に書く内容が変わらない」は、テストの固定ページで流した結果を前後で比べて確かめる。本番のページでの比較はしない
- マルエーの1ファイルの目安 600 行は、今のマリックス（892 行）より小さく、役割を4つに分けたときに自然に収まる大きさとして置いた。マリックスは分けない（長いメソッドを分けるのは US3 の範囲で必要な分だけ）
- `BaseScraper` に置くか別の共通の場所に置くかは plan で決める
- Web アプリ・DB の列・通知メールには触らない

## Out of Scope

- マリックスラインのファイルを複数に分けること
- Web アプリ（PHP）の整理
- 3 社目のスクレイパーの追加
- テストの書き直し・整理（差し替え先の変更を除く）
- 整理中に見つけたバグの修正（別の Issue にする）
