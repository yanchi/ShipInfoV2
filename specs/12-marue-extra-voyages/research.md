# Research: マルエーフェリーの臨時便を港別ステータスに出す

**Date**: 2026-10-26 | **Spec**: [spec.md](spec.md)

## R1. 臨時便のスケジュールの読み方

**Decision**: 詳細ページの `div.status-archive` の中の `p` を上から順に読む。`【臨時便(上り)】`・`【臨時便(下り)】`（全角・半角の括弧どちらも）の行で臨時便を1つ始め、次のどれかで終える。

- 次の `【…】` の行
- `《…》` の行（乗船手続き時間。ここから先はスケジュールではない）
- `status-archive` の終わり

臨時便の中の行は次のように読む。

| 行 | 読み方 |
|---|---|
| `M月D日(曜)港名　HH:MM(出港)` | 始発港。出港だけ |
| `M月D日(曜)港名　HH:MM(入港)/HH:MM(出港)` | 途中の港 |
| `M月D日(曜)港名　HH:MM(入港)` | 終点。入港だけ |
| `※ …寄港いたしません。` | 寄港しない港の文。行の詳細に使う |
| 空行（`&nbsp;`）・そのほかの `※` の行 | 読み飛ばす |
| 上のどれでもない行 | 読めない行（R3） |

- 港名は `PortResolver.resolve()` で決める（「鹿児島新港」「名瀬港」は別名にある）
- 年は抜粋の便の行と同じく、今日にいちばん近い年（`_parse_voyages()` と同じ決め方。共通の関数にする）

**Rationale**: 2026-10-26 の波之上の詳細ページ（`samples/naminoue_detail_2026-10-26.html`）は、この形で `p` 1つに1行で書かれている。港別情報の本文（`port_notice._detail_body()`）は定型の注意書き（「台風の影響や」）が無いと本文を使わないが、このページには定型の注意書きが無い。そのため臨時便は `_detail_body()` に頼らず、`status-archive` から直接読む。

**Alternatives considered**:
- 本文全体を1つの文字列にして正規表現で読む → `p` の区切りが「行」として使えなくなり、終点（入港だけ）と途中の港の見分けが崩れやすい
- `_detail_body()` を使う → 上のとおり、このページでは None になる

## R2. 便と方向・航路の決め方

**Decision**:
- 方向は見出しの「上り」「下り」。航路は `_route_directions()` で方向から引く
- 港の並びは、その航路の `route_stops` の順に沿っていなければならない（逆順・同じ港が2回は読めない扱い）。航路に無い港（伊延・平土野など）も読めない扱い
- 1つの臨時便の行は、出港時刻のある港ごとに1行（`departure_statuses` のキー：航路・港・出港日・船名）
- `scheduled_departure_at`：その港の出港時刻
- `scheduled_arrival_at`：終点の入港時刻（便検索の「下船日時」と同じ意味。港別ページの「〜着」と、便の照合に使う）
- 終点に入港の行が無い臨時便は読めない扱い（便を特定できないため）

**Rationale**: 便検索の行は「その港の乗船日時」「終点の下船日時」を持つ。同じ意味にしておけば、画面（着時刻）と、R5 の便のまとめ方（船・航路・下船日時）がそのまま使える。

## R3. 読めないときの扱い（FR-007）

**Decision**: 次のどれかがあれば、その臨時便は1行も作らない。警告 `extra_voyage_unreadable`（船名・見出し・読めなかった行）を出す。

- 読めない行がある
- 港が航路に無い・順番が合わない
- 日付と曜日が合わない
- 途中の港で出港時刻が無い
- 終点の入港が無い
- 時刻が前の港より前になる

さらに、その船は「読めなかった船」にする。その回は、その船の臨時便の行を1つも消さない（R6）。

**Rationale**: 公式は日付を書き間違える（2026-10-26 の【欠航】に「9月27日(火)」とある）。間違った日に臨時便を出すより、出さないほうが安全。前回作った行は、読めなかったことを取りやめとみなさず残す。

## R4. 臨時便の行の状態

**Decision**: 新しい状態 `extra`（臨時便）を足す。`departure_statuses` だけで使う。

- 抜粋に、その臨時便に合う便の行がある場合。合うのは、方向が同じで日付が臨時便の始発港の出港日と同じ行だけ。`_voyage_line()` の2段目（途中の港から書いた行を出港日〜到着日の範囲で合わせる）は使わない（PR #87 レビュー）。たとえば抜粋の「■10月26日 名瀬港発下り便…欠航」は、10/25 鹿児島発の定期便の行。10/26 鹿児島発の臨時便（10/27 着）でも範囲に入ってしまい、臨時便の3港が定期便の文で欠航になるため
  - 行の状態が cancelled・suspended・delayed なら、その状態にする
  - 詳細は抜粋の文（`_ship_detail_text()`）にする
- それ以外は `extra`
  - 詳細は寄港しない港の文。無ければ None
- 港別情報（抜港・港変更）は当てない

`OperationStatusEnum`（Python・PHP）に `extra` を足す。DB の `departure_statuses.status` は VARCHAR(32) なので、マイグレーションはいらない。`operation_statuses.status`（ENUM）には書かない。

**Rationale**: 臨時便は時刻も寄港地も定期便と違う。だから通常運航（operating）では出さない（Clarifications）。抜粋の「臨時便運航」は 11 で operating として読むけれど、臨時便の行の状態としては「臨時便」のままにする。

**Alternatives considered**:
- operating ＋ 詳細に「臨時便」 → バッジが通常運航になり、定期便どおりと読まれる（ユーザー指摘で却下）
- 臨時便かどうかを別の列に持つ → マイグレーションが要り、画面・通知も列を見る分岐が増える。状態にすれば今の「状態でバッジ・通知を決める」仕組みにそのまま乗る

## R5. 臨時便の行の見分け方（FR-013・FR-014）

**Decision**: 臨時便の行は `source_url` を船の詳細ページの URL にする。便検索から作る行は今までどおり `SEARCH_URL`。臨時便の行かどうかは、`source_url` が NULL でも `SEARCH_URL` でもないことで見分ける（状態は欠航になることがあるので、状態では見分けない）。

便検索の便の判定で DB を読むところは、全部 `source_url` が NULL か `SEARCH_URL` の行に絞る（`_SEARCH_ROWS` 条件）。

| メソッド | 何に使う | 臨時便の行が混ざると |
|---|---|---|
| `_recorded_voyages()` | 今の便を決める | 臨時便が「今の便」になり、定期便の判定がずれる |
| `_recorded_voyage()` | 出港済みか・前回のステータス | 10/26 鹿児島発の臨時便（10/27 13:50 那覇着）と、10/25 鹿児島発の定期便（10/26 19:00 那覇着）は差が24時間未満。同じ便として混ざる |
| `_recorded_search_keys()` | 2日先以降の強制検索 | 欠航になった臨時便の行で、毎回検索になる |
| `_needs_far_search()` | 2日先以降の検索間隔 | 臨時便の行の `checked_at` が毎回進み、そのキーの便検索が止まる |

**Rationale**: 臨時便の行を消すときや、検索の行で整理するときも、同じ条件で見分けられる。`source_url` は今は画面に出していない。

## R6. 臨時便の行を消す（FR-008・FR-013）

**Decision**:

1. **便検索の整理で消さない**：`BaseScraper._upsert_departures()` のルール5（`replace_scope`）は、同じ `source_url` の行だけを消すようにする。今 `replace_scope` を使っているのはマルエーの便検索の行だけで、どれも `SEARCH_URL` なので、ほかの動きは変わらない
2. **取りやめで消す**：`MarueFerry._upsert_departures()` で親を呼んだあとに消す。消すのは、次の全部に当てはまる臨時便の行
   - 船：その回に詳細ページを取れて、読めない臨時便が無かった船
   - 出港日：今日〜`MARUE_SEARCH_DAYS_AHEAD` 日先（FR-009 の範囲）
   - その回に書かなかったキー
   - 便（船・航路・`scheduled_arrival_at`）の行の `scheduled_departure_at` の最小が今より後（始発港を出港していない）。この最小は、出港日で絞らずにその便の行を全部読んで求める。前日に始発港を出た便は、始発港の行の出港日が範囲の外にあるため（analyze U1）
   - 便の中に始発港（航路の最初の港）の行が無い便は、出港済みとみなして消さない。始発港の行が無いのは、初めて読んだときに始発港をもう出ていた（出港済みの行は作らない）か、始発港で便検索とぶつかった（R7）とき。残りの行だけで最小を取ると、走っている便を消してしまう（analyze U4）。便検索とぶつかった臨時便が出港前に取りやめになった場合は行が残るが、消すより残すほうが安全
3. 書いた行の更新は、親の `freeze_after_departure`（港ごと）のまま
4. 消す対象の船は、その回に詳細ページを取れて、読めない臨時便が1つも無かった船だけ（`ExtraParse.complete`）。読めない臨時便がある船も、読めた臨時便の行は作る（FR-007。PR #87 レビュー）

**既知の取りこぼし**（PR #87 レビュー。起きたら対応する）:
- 船の枠が鹿児島航路ページから消えると、その船の詳細ページを取りに行かないので、臨時便の行は消す対象にならない。終点の到着予定時刻を過ぎるまで残る
- 終点の入港時刻が変わると、同じ臨時便が別の便（`scheduled_arrival_at` 違い）として2組に分かれる（下の注記）。行を作るときに、同じ船・航路で `scheduled_arrival_at` が違い、差が24時間未満の臨時便の行が DB にあれば、警告 `extra_voyage_arrival_changed` を出す

**注記**: 時刻が変わって終点の入港（`scheduled_arrival_at`）がずれると、新しい行と古い行が別の便にまとまる。始発港を出る前なら古い行は消える。出た後は古い行が出港済みの港の行として残る（新しい時刻の行は、まだ出ていない港だけにできる）。実害は小さいので、このままにする（analyze U2）

**Rationale**: 「出港済み」を便ごとに見るのは、行を消すかどうかだけ（Clarifications）。中身の更新は今の行と同じく港ごとに止める。消す処理は臨時便という会社固有の決まりなので、マルエーの中に置く。Base には「同じ出どころの行だけを整理する」という一般的な直しだけ入れる。

**Alternatives considered**:
- `replace_source` を使う → 港ごとに消すので、便の途中で告知が消えたときに、まだ寄っていない港の行が消える（spec の Edge Cases）
- `parse_departures()` の中で消す → parse に副作用が入る

## R7. 便検索の行とぶつかるとき（FR-003）

**Decision**: 臨時便の行のキー（航路・港・出港日・船名）が次のどちらかに当たるときは、臨時便の行を作らない。

- この回の便検索の記録にある
- DB に `_SEARCH_ROWS` の行がある（2日先以降で、この回に検索しなかったキー）

さらに、この回の便検索の記録に出港時刻があり、臨時便と違えば、別の便とみなす（時刻の無い抜港の記録には付けない）。その記録の `status_detail` の後ろに「（臨時便 HH:MM発あり）」を足し、警告 `extra_voyage_key_conflict` を出す。

**Rationale**: キーは1つしか持てない。定期便の状態（欠航など）は残し、臨時便が出ることだけを伝える。

このとき抜粋の便の行（「■10月28日（水）那覇港発上り便…欠航」）は、同じ方向・同じ始発港の出港日の定期便と臨時便の両方に当たる。だから定期便が便検索（この回の記録か、DB の `_SEARCH_ROWS` の行）にあれば、抜粋の行は定期便のものとみなし、臨時便は extra のままにする（R4。analyze A2）。

## R8. 港別情報から臨時便の告知を除く（FR-015）

**Decision**: `port_notice._detail_body()` で、`【臨時便…】` の行から次の `【…】` の行までの `p` を飛ばす。**定型の注意書き（`BOILERPLATE_MARKER`「台風の影響や」）の確かめは、飛ばしている間も続ける**。飛ばしている途中でマーカーが出たら、そこで今までどおり本文を返す（PR #87 レビュー）。マーカーまで飛ばしてしまうと `_detail_body()` が None を返し、その船の定期便の港別情報（抜港・港変更）が黙って全部消えるため。

飛ばす範囲は、臨時便の読み取り（R1。《…》で閉じる）より広く、次の【…】か定型の注意書きの手前までにする。臨時便の後ろの注意書き（「※港変更になった場合…」「徳之島で港変更がある場合…」）は臨時便の話か定期便の話か分からないため、港別情報では安全側で使わない（今も仮定の文として捨てられているので、結果は変わらない）。

**Rationale**: 今の 2026-10-26 のページには定型の注意書きが無く、本文は使われていない。それでも、注意書きのある臨時便のページが来ると「寄港いたしません」が定期便の抜港になる。そのため本文を読む側で除く。

## R9. 画面（FR-005・FR-016・FR-017）

**Decision**:
- `OperationStatusEnum::Extra = 'extra'`
  - `label()` は「臨時便」
  - `isIrregular()` は true（通知の対象。US4 は今の仕組みのまま載る）
- バッジは `◆ 臨時便`。色は青系（背景 `#dbe9ff`・文字 `#0b4a8b`）で、ほかのどの状態とも違う色にする
- `PortBoardEntry::isAlert()` に Extra を足す
  - 異常の要約に入れる（FR-017）
  - 行を目立たせる（`port-entry--extra`）
  - 出港済みでも薄くしない
- `_status_warning`（「出港時間・寄港地が変更になってる可能性…」）も Extra で出す
- 凡例：抜港と欠航の間に「便検索に無い臨時の便。時刻・寄港地は定期便と違う」
- トップの会社カード（FR-016）
  - `PortBoardDay::firstExtraDepartureOf(companyId, direction)`：今日その方向の、Extra の便のうち出港時刻がいちばん早いもの（港名・時刻）
  - `StatusController::index()` で航路ごとに求め、航路のバッジの下に「◆ 臨時便 鹿児島 16:00発」を出す
- 途中の港だけの日（10/27 下り）は、今の `midwayDisplay()` で全部 Extra ならバッジが「臨時便」になる。FR-016 の行も出す（港と時刻が分かる）

- `StatusController::midwayDisplay()`：Extra を `isAlert()` に入れると、途中の港の便が「定期便の通常運航＋臨時便」のときに「スケジュール変更」になってしまう。そのため Extra の entry を除いて今までどおり決め、Extra しか無いときだけ「臨時便」のバッジにする（PR #87 レビュー）
- 通知メールの `IrregularService::statusText()`：航路×日付が通常運航以外でなく、港の行が全部 Extra のときは「臨時便あり」（航路が Operating なら「通常運航（臨時便あり）」）。今のままだと、10/28 上り（航路は便なし）が「情報なし（途中の港に変更あり）」になり、那覇から出る臨時便まるごとを「途中の港の変更」と書いてしまう（PR #87 レビュー）

**Rationale**: 抜港（9-marue-port-skip）を足したときと同じ場所を直す。

## R10. 出す順番（デプロイ）

**Decision**: PHP の Enum に Extra が無いまま、スクレイパーが `extra` を書くと、Doctrine が読めずにページがエラーになる。だから PHP とスクレイパーを同じ PR・同じイメージで出す（今のデプロイは1回で両方を入れ替える）。tasks では PHP の Enum を先に足す。

**ロールバック**（PR #87 レビュー）：`extra` の行ができたあとで前の GHCR イメージに戻すと、`OperationStatusEnum::from('extra')` が例外を投げ、/ports・トップ・会社ページ・`app:notify-irregular-statuses` が全部失敗する。戻すときは、先に `DELETE FROM departure_statuses WHERE status = 'extra'` を流してから戻す。手順は quickstart.md と deploy/README.md に書く。抜粋で欠航などになった臨時便の行（`status` が extra でない）は、戻した後も読めるので残してよい
